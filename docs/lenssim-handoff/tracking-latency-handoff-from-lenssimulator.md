# 트래킹 지연("렌즈가 눈을 끌고 다님") 해결 인사이트 — LensSimulator → IrisLensSDK 핸드오프

작성: 2026-06-15 (LensSimulator 세션)
근거: LensSimulator `docs/decisions/0002-tracking-rendering-stack.md`, `0005-frame-synced-rendering.md` + 실기기(Galaxy S23+) 검증

> 이 문서는 **구현 코드 이식이 아니라 진단·교훈 인사이트**다. IrisLensSDK는 C++ 단일 코어라
> 구조가 다르므로, 아래 "원인 진단"과 "함정 목록"을 자기 아키텍처에 맞게 적용할 것.

---

## TL;DR

움직임 중 렌즈가 눈을 늦게 따라가며 미끄러지는 문제의 **진짜 원인은 One-Euro 필터 지연도, 추론
속도도 아니라 "화면 픽셀과 랜드마크의 프레임 불일치"였다.** 화면은 최신 카메라 프레임을 그리는데
랜드마크는 ~2프레임 전 분석 프레임 기준이라, 필터를 아무리 손봐도 해소되지 않는다. 해결은
①LIVE_STREAM → VIDEO 동기 추론 ②**랜드마크가 계산된 그 프레임을 화면에 그리는 프레임 동기 렌더링**.

---

## 1. 증상

- 고개/시선 이동 시 렌즈(홍채 오버레이)가 눈을 **끌고 다닌다** — 정지하면 다시 맞음.
- 빠른 움직임일수록 어긋남이 큼.

## 2. 근본 원인 진단 — 여기가 핵심 인사이트

처음엔 "필터 지연" 또는 "추론이 느려서"라고 의심하게 된다. **둘 다 틀렸다.**

진단 방법: **디버그 메시 오버레이로 raw 랜드마크(필터 적용 전, MediaPipe 출력 그대로)를 화면에
점으로 그려봤다.** 그 결과 — 필터를 거치기도 전에 **raw 랜드마크가 이미 화면 프레임보다 늦어
있었다.** 즉 어긋남은 필터가 만든 게 아니다.

원인은 **파이프라인의 프레임 불일치**:
- 화면(렌더)은 `updateTexImage`로 들어온 **최신** 카메라 프레임을 그린다.
- 랜드마크는 추론(≤15ms) + 분석 스레드 핸드오프가 누적된 **~2프레임 전** 분석 프레임 기준이다.
- 두 프레임이 다르니, 빠르게 움직이면 "현재 픽셀 위에 과거 좌표"가 얹힌다.

**교훈: 트래킹 어긋남을 보면 필터부터 만지지 말고, 먼저 raw 랜드마크를 화면에 오버레이해서
"필터 이전부터 늦는가"를 확인하라.** 늦으면 필터 문제가 아니라 프레임 동기 문제다.

## 3. 해결책

### (a) LIVE_STREAM → VIDEO 동기 추론 (ADR-0002)
- MediaPipe `LIVE_STREAM`의 내부 큐잉이 1~2프레임 지연을 더한다(디버그 메시로 실측).
- `RunningMode.VIDEO` 동기 `detectForVideo`로 전환. 카메라 백프레셔(CameraX KEEP_ONLY_LATEST
  등가)가 추론 중 도착한 묵은 프레임을 자동 폐기 → 항상 최신만 추론.
- C++ 코어라면 TFLite 호출을 프레임 동기 호출로 두고, 입력 큐를 1-deep(최신만 유지)으로.

### (b) 프레임 동기 렌더링 — 가장 결정적 (ADR-0005)
핵심 발상: **렌더가 "최신 카메라 프레임"이 아니라 "랜드마크가 계산된 그 프레임"을 그린다.**
- 카메라 프레임을 작은 **링버퍼(4장)** 에 복사해 둔다 (각 엔트리 = 텍스처 + 변환행렬 + 타임스탬프).
- 추적 스냅샷에 **그 프레임의 센서 타임스탬프(ns)** 를 동반시킨다.
- 렌더 시 스냅샷 타임스탬프와 **|Δ| 최소인 링 엔트리**를 골라 그 위에 렌즈를 합성.
- → 랜드마크와 픽셀이 같은 프레임이 되어 정합이 완벽해진다.

**클럭 도메인 함정 (반드시 주의)**: 카메라 센서 타임스탬프와 추론 엔진이 쓰는 타임스탬프가
**다른 클럭**일 수 있다 (LensSimulator는 센서 ns vs 분석 스레드 uptime ms). 매칭은 같은
클럭끼리 해야 한다. 방어: |Δ|가 **연속 N회**(우리는 5회) 비정상(>1초)이면 클럭 불일치로 보고
최신 엔트리로 강등 + 로그. 단발 초과(콜드 스타트의 묵은 첫 프레임)로는 강등하지 않는다 —
진짜 불일치는 오프셋이 일정하게 유지되므로 "연속" 카운트가 두 경우를 구분한다.

**폴백 설계 (오류가 아니라 기능 강등)**: 스냅샷 없음/링 빔/|Δ|>150ms → 최신 엔트리로 자연
강등. 링 생성 실패 → 직접 경로로 영구 강등 + 로그 1회. 킬 스위치 플래그 유지.

**수용한 대가**: 화면이 "마지막 분석 프레임"을 보여주므로 거울 지연 +2~3프레임(~70–100ms).
셀피 거울에서는 **지연보다 렌즈-눈 어긋남이 훨씬 눈에 띈다** — 실기기 비교로 확인 후 수용 결정.

## 4. 기각된 함정 — 시간 낭비 방지

이미 시도하고 버린 것들이다. IrisLensSDK에서 반복하지 말 것:

- **속도 예측 / 외삽(lead)**: 랜드마크를 속도로 앞당기면, **방향 전환 순간 과거 방향으로 좌표를
  밀어 오히려 더 크게 틀어진다.** 기저벡터(타원화)까지 변형돼 렌즈가 찌그러진다. 기각.
- **One-Euro beta 강화(예: 0.1)**: 원인이 필터가 아니라서 해소 불가. 지연만 줄이려다 지터 증가.
- **분석 완료까지 렌더 대기**: 추론 스파이크가 곧장 프리뷰 fps 저하로 전이된다. 금지.

## 5. One-Euro 튜닝 인사이트

- **프레임 동기 체제에서는 화면 = 랜드마크 프레임**이라, 필터 지연이 곧 화면 어긋남이 된다.
  따라서 **near-raw 튜닝**: 1프레임 스파이크만 억제하는 약한 필터(우리 검증값 `min_cutoff=3.0,
  beta=0.3`)로 raw에 수렴시킨다.
- **프레임 동기 이전 아키텍처**라면 더 강한 필터(우리의 동기 이전 검증값 `0.5/0.007`)가 기준.
  즉 필터 세기는 "프레임 동기를 했는가"에 종속된다 — 먼저 동기를 정하고 필터를 맞춰라.
- MediaPipe 프로덕션 예시값(`min_cutoff 0.05/beta 80`)은 객체 스케일 정규화 전제라 **직접 적용
  금지.**
- **값 정본은 문서가 아니라 코드 상수다.** LensSimulator에서 "1.0→0.3" 문서 드리프트를 (역으로)
  IrisLensSDK 교차 검토가 잡아낸 적이 있다 — 핸드오프 시 문서값을 신뢰하지 말고 코드를 확인할 것.

## 6. IrisLensSDK 적용 체크리스트

- [ ] 먼저 raw 랜드마크를 화면에 오버레이해서 "필터 이전부터 늦는가" 확인 (진단 우선)
- [ ] TFLite 추론 입력을 1-deep 최신만 유지 (LIVE_STREAM류 큐잉 제거)
- [ ] 카메라 프레임 링버퍼 + 타임스탬프 매칭 렌더 (플랫폼별: Android OES/SurfaceTexture,
      iOS CVPixelBuffer presentationTimeStamp, Web은 video.currentTime/RVFC 메타)
- [ ] 센서 클럭 vs 추론 클럭 도메인 일치 확인 + 연속 카운트 기반 강등 방어
- [ ] 필터 세기는 프레임 동기 여부에 맞춰 결정 (동기 후 near-raw)
- [ ] 거울 지연 trade-off는 실기기 육안 비교로 수용 결정 (정량 아닌 지각 기준)
