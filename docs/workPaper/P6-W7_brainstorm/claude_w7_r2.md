## T1 — 6.3 메타 저장: JSON(내 R1 입장) vs 하드코드 레지스트리(Codex)

**입장: 유지 (JSON), 단 Codex 논리의 정당한 부분 1개 수용.**

Codex 소수 의견의 핵심은 두 가지였다:
1. "메타는 내부 material 필드인데 외부 JSON 파이프라인을 새로 여는 게 과하다"
2. "흔들렸던 축이라 편집 편의성보다 결정적·버전 고정 소스가 낫다"

평가:
- **(1)에 대한 반박:** "내부 material 필드"라는 것은 *런타임 표현*의 문제이지 *저장 소스*의 문제가 아니다. JSON은 빌드/로딩 시점에 파싱되어 동일한 내부 material 구조체로 들어간다. 공개 `LensConfig`는 그대로이므로 "외부에 노출"되는 것도 아니다. JSON 파일은 앱 assets에 git 체크인되는 내부 산출물이지 공개 API surface가 아니다. → Codex의 (1)은 "저장 형식 = API 노출"이라는 혼동에 기반.
- **(2)에 대한 부분 수용:** "결정적·버전 고정"은 정당한 우려다. 하지만 JSON도 **git 체크인하면 버전 고정 효과는 동일**하다 (R1 synthesis §2 완화 조치). 차이는 "재빌드 없이 디자이너가 편집 가능"이라는 JSON의 장점인데, SKU 20개 규모에서 이 장점이 크지 않다는 Codex 지적은 일리 있다. 그러나 **단점도 없다** — 하드코드 대비 JSON이 잃는 것은 "타입 체크 컴파일 타임 보장"인데, 이건 로더에 스키마 검증 + default false fallback으로 메운다.

**결론:** JSON 유지. Codex의 "버전 고정" 우려는 git 체크인으로 흡수됨이 R1에서 이미 정리됐고 R2에서 새 논거 없음. 다만 한 가지 **양보**: 하드코드가 "더 단순하다"는 점은 사실이므로, JSON 로더 구현이 200줄을 넘어 복잡해지면 (SDK 공용 파서가 없어 경량 파서를 새로 짜야 하는 경우) 그때는 20개 하드코드 레지스트리가 합리적 대안이 된다. **즉 "JSON 우선, 파서 비용이 크면 하드코드 폴백"이 정직한 결론.** 이건 R1 다수안을 뒤집는 게 아니라 구현 시 판단 기준을 명시한 것.

## T2 — 6.5 정확도 기준: 10/10 엄수(내 R1 입장) vs 9/10 완화(Gemini)

**입장: 유지 (10/10 엄수 + 개별 메타 fallback). Gemini 논리의 약점 명시.**

Gemini 소수 의견의 핵심:
1. "10/10은 실기기 노이즈/텍스처 압축 손실 고려 시 과도하게 엄격"
2. "9/10 도달 시에도 fallback 채택하되, 오판 1개는 임계값 튜닝으로 10/10 지향"

평가:
- **(1)에 대한 반박:** 이건 **R4 실기기 실측에 의해 이미 기각된 가설**이다. Gemini는 "노이즈로 10/10이 안 될 수 있다"는 *이론적 가능성*을 말하는데, R4에서 5+5 SKU 전수 10/10이 *실측으로 달성*됐다 (W7 §1 R4 patch). 이론적 우려 vs 실측 팩트가 충돌하면 팩트를 따른다 (메모리 `feedback_real_data_first`, `feedback_qualitative_device_judgment`). → Gemini (1)의 약점: 실측을 이론으로 반박하려 함.
- **(2)에 대한 분석:** Gemini의 "9/10 채택 + 튜닝으로 10/10 지향"은 사실 **다수안과 운영상 거의 같은 결과**를 낸다. 다수안도 "10/10 엄수하되 실패 SKU는 개별 메타 fallback"이다. 차이는 *프레이밍*:
  - Gemini안: "rule을 9/10으로 완화" → 자동감지가 1개 틀려도 OK라고 *rule 자체*를 느슨하게.
  - 다수안: "rule은 10/10 유지, 틀린 SKU만 메타로 명시 예외" → rule은 엄격, 예외는 데이터로 관리.
  - **다수안이 우월한 이유:** rule을 9/10으로 풀면 "어느 1개가 틀려도 되는가"가 불명확해져 false positive가 *어느 SKU에서나* 허용된다. 다수안은 "틀린 그 SKU만" 명시 fallback이라 통제 가능. → 운영 안전성은 다수안이 높다.

**결론:** 10/10 엄수 유지. Gemini의 노이즈 우려는 R4 실측으로 기각됐고, 9/10 완화는 통제력만 잃고 얻는 게 없다. **단 Gemini 우려를 흡수하는 조항은 이미 있음** (실패 SKU 개별 메타 fallback + 배포 후 1개월 모니터링). 이게 Gemini가 걱정한 "실기기에서 실제로 틀리는 경우"의 안전망이다.

**Codex/Claude에게 던진 역질문("10/10이 너무 빡빡해 메타 fallback 남발 위험은?")에 대한 자답:** 남발 위험 낮음. R4 실측 10/10이면 fallback이 필요한 SKU는 거의 0에 수렴. fallback은 "배포 후 미발견 디바이스 변수"에 대한 보험이지 일상 운영 도구가 아니다. 남발된다면 그건 자동감지가 실제로 9/10 이하라는 신호 → 그때는 W7 범위 밖 재벤치(별도 문서) 트리거.

## 자기비판 (편향 경계)

- **방어적 고착 경계:** R2에서 내가 R1 입장을 100% 유지했는데, 이게 "내 R1이 옳다"는 고착인지 점검. → 6.3에서 Codex "더 단순" 논거를 부분 수용(파서 비용 폴백 조건)했고, 6.5는 R4 실측이라는 외부 팩트에 근거하므로 고착 아님. 만약 Codex/Gemini가 R2에서 R4 실측을 뒤집는 *새 데이터*를 제시하면 즉시 재검토.
- **타 모델 쏠림 경계:** Codex 10/10 엄수안과 일치하지만, R4 실측 일치이지 Codex 추종이 아님. Gemini를 다수로 누른 것도 "다수라서"가 아니라 9/10의 통제력 약점 때문.
- **3번 뒤집힘 종결 의지:** 이 R2의 목적은 새 뒤집기가 아니라 R1 수렴이 견고한지 확인. 지금까지로는 견고하다고 판단. Codex/Gemini R2가 새 논거를 내지 않으면 R1 결론 그대로 구현 착수 권고.
