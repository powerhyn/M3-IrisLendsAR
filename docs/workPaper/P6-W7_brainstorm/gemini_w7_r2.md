## 2. 핵심 쟁점 평가 및 토론

### T1 — 6.3 메타 저장: JSON(Gemini/Claude) vs 하드코드(Codex)

*   **Codex 논리에 대한 평가:** Codex가 우려하는 "버전 고정/결정적 소스"와 "소수 SKU(20개)에 대한 오버헤드" 논리는 시스템의 견고함 측면에서 타당함. 특히 내부 material 필드를 다루는 만큼 코드 내 관리가 안전해 보일 수 있음.
*   **반론 및 유지 근거:** 
    1.  **콘텐츠와 로직의 분리:** 림발 플래그는 엔진 로직이라기보다 '에셋 프로파일'에 가까움. 이를 하드코딩할 경우 에셋 하나를 추가할 때마다 SDK 전체를 다시 빌드하고 배포해야 하는 비효율이 발생함.
    2.  **재빌드 사이클 제거의 가치:** 디자이너나 QA가 `lens_meta.json`만 수정하여 실기기에서 즉시 림발 정책 변화를 확인하는 것은 개발 생산성 면에서 압도적임. 
    3.  **결정론적 우려 해소:** JSON 파일을 Git 리포지토리에 체크인하여 관리하므로, Codex가 강조하는 "버전별 일관성"은 코드 방식과 동일한 수준으로 보장됨.

### T2 — 6.5 자동감지 정확도: 10/10 엄수(Claude/Codex) vs 9/10 완화(Gemini)

*   **입장 수정:** 본인은 R1의 '9/10 완화안'을 철회하고 **'10/10 엄수'로 선회함**.
*   **상대 논리 수용 근거:**
    1.  **실측 팩트 우선:** Claude와 Codex가 지적했듯, R4 실기기 테스트에서 이미 5개 SKU가 10/10을 달성했음. 이론적인 '노이즈 우려'보다 실제 데이터가 보여주는 '달성 가능성'이 더 강력한 근거임.
    2.  **편향 경계:** Claude가 림발 정책에서 여러 번 입장을 바꿨던 히스토리를 고려할 때, 팩트(R4 결과)에 기반한 가장 엄격한 기준을 유지하는 것이 정책의 안정성을 높이는 길임.
    3.  **Fallback의 안전성:** 10/10 기준이 너무 엄격해 실패하더라도, 우리에게는 이미 JSON 메타데이터(T1)라는 확실한 Fallback이 존재함. 무리하게 감지 임계값을 낮춰 False Positive를 유발할 리스크를 감수할 필요가 없음.
