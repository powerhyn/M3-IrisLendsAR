## 1. T1 — 6.3 메타 저장 방식

### 내 R1 입장

**유지.** W7 메타 저장은 JSON 파일보다 코드 내 하드코드 레지스트리(`LensSkuRegistry`)가 낫다.

### Gemini/Claude JSON 다수안 평가

Gemini와 Claude의 JSON 주장은 다음 장점에 기대고 있다.

- SKU 추가나 메타 수정 시 바이너리 재빌드 없이 반영 가능하다.
- 디자이너나 에셋 담당자가 직접 편집하기 쉽다.
- Phase 7 이후 설정 확장에 유리하다.
- git 체크인, 기본값 `false` fallback, WARN 로그로 결정성과 누락 위험을 낮출 수 있다.

이 논리는 "메타가 앱/SDK 바이너리와 독립적으로 배포되고, SKU 메타를 비개발자가 자주 수정하며, 필드가 계속 늘어난다"는 전제가 맞으면 타당하다. 하지만 R1 §6.3의 W7 범위에서는 그 전제가 아직 강하지 않다. 지금 논점은 내부 material 정책 필드 몇 개를 소수 SKU에 고정하는 일이고, 림발 정책은 R1~R4에서 이미 판단이 흔들렸던 축이다. 이 상황에서는 편집 편의성보다 코드 리뷰를 통과하는 단일 결정 소스가 더 중요하다.

JSON 완화책도 일부 위험만 줄인다. git 체크인은 버전 추적을 제공하지만, 런타임 로더/파서/스키마/에셋 패키징 경로라는 별도 실패면을 새로 만든다. 기본값 `false` fallback과 WARN 로그는 앱 중단을 막지만, 메타 누락을 조용한 시각 품질 저하로 바꾸는 장치이기도 하다. 즉, 완화책은 "깨지지 않게" 만들 뿐 "잘못된 정책이 들어가지 않게" 만들지는 않는다.

Claude의 구체 스키마 제안은 구현 가능성이 높다는 점에서 Gemini보다 실무적이다. 다만 `prefers_crl`, `has_baked_limbal`, `prefers_graphic_outline` 같은 정책 필드는 렌더링 동작과 직접 연결된다. 이 필드를 외부 JSON 파이프라인으로 여는 순간, 단순한 데이터 편집이 아니라 렌더링 정책 변경 채널을 하나 더 만드는 셈이다. SKU가 20개 안팎이라면 그 비용은 재빌드 회피 이익보다 크다.

### R2 판단

**하드코드 `LensSkuRegistry` 유지.**  
JSON 다수안의 완화 조치는 결정성 우려를 완전히 흡수하지 못한다. W7에서는 SKU 수와 필드 수가 작고, 정책 변경의 blast radius가 렌더링 품질에 직접 닿기 때문에 하드코드 레지스트리가 더 단순하고 검증 가능하다.

## 2. T2 — 6.5 자동감지 정확도 기준

### 내 R1 입장

**유지.** 자동감지 정확도 기준은 `10/10` 엄수, 실패 SKU는 개별 메타 fallback으로 처리한다.

### Gemini 9/10 완화안 평가

Gemini의 9/10 완화안은 실기기 노이즈와 텍스처 압축 손실을 고려하면 10/10이 과도하게 엄격할 수 있다는 주장이다. 이 우려 자체는 일반론으로는 맞다. 자동감지 로직은 기기, 압축, 샘플링 차이에 영향을 받을 수 있으므로, 테스트 표본이 넓어지면 일부 SKU에서 흔들릴 가능성은 있다.

하지만 R2 기준선에는 이미 R4 실기기에서 `10/10` 달성이 가능했다는 팩트가 있다. 또한 다수안은 "자동감지를 무조건 통과시켜야 한다"가 아니라 "자동감지 기준은 10/10으로 두고, 실패 SKU만 개별 메타 fallback한다"이다. 이 구조는 Gemini의 노이즈 우려를 이미 흡수한다. 노이즈로 특정 SKU가 흔들리면 전역 기준을 낮추는 대신 그 SKU를 메타로 고정하면 된다.

9/10 완화안의 약점은 false positive 1건을 정책적으로 허용한다는 점이다. 림발 정책에서 비용이 큰 쪽은 놓친 림발보다 잘못 켠 셰이더 림발이다. 특히 이미 baked limbal이나 그래픽 아웃라인이 있는 SKU에 셰이더 림발을 중첩하면 디자인 의도가 바로 깨진다. R4에서 10/10 경로가 확인된 뒤에도 9/10을 기본 기준으로 낮추는 것은 얻는 안정성보다 잃는 정확성이 크다.

### Claude 10/10 엄수안 평가

Claude의 10/10 엄수 근거는 Codex R1과 같은 방향이며, 특히 "R4 실기기 10/10 증거"를 기준선으로 삼은 점은 타당하다. Claude가 과거 림발 정책에서 입장을 여러 번 바꾼 맥락을 명시하고, 이번에는 주관적 유연성보다 실측 사실을 우선한 것도 R2 목적에 맞다.

다만 10/10 엄수가 운영에서 메타 fallback을 남발할 위험은 이론적으로 있다. 그 위험은 기준을 낮춰 해결할 문제가 아니라 fallback 대상 SKU를 명시적으로 관리해서 해결할 문제다. 자동감지가 실패하는 SKU가 많아진다면 그것은 6.5의 기준 완화 근거라기보다 자동감지 기본축의 신뢰도가 낮다는 신호다. R1 범위에서는 그 상황이 확인되지 않았다.

### R2 판단

**10/10 엄수 유지.**  
Gemini의 9/10 완화안은 실기기 노이즈라는 일반 리스크를 잘 지적하지만, R4의 10/10 달성 사실과 "실패 SKU만 개별 메타 fallback"이라는 다수안 앞에서는 기준을 낮출 만큼 설득력이 없다.

## 3. 합의 5개 재확인

- **6.1 자동감지 ROI `[0.85,1.0]`: 유지.** `[0.80,1.0]`로 넓힐 새 근거가 없고, false positive 회피가 우선이다.
- **6.2 임계값 `0.75`: 유지.** 0.70/0.80으로 바꿀 근거가 없으며, W7에서는 정확도 기준과 임계값 변수를 동시에 흔들지 않는 편이 낫다.
- **6.4 메타 누락 로그 WARN: 유지.** DEBUG는 누락 인지가 약하고 ERROR는 런타임 의미가 과하다.
- **6.6 엔비_샤모 `prefers_graphic_outline`: 유지.** 일반 baked limbal과 다른 예외를 별도 플래그로 표현하고 셰이더 림발은 OFF로 두는 결론을 바꿀 이유가 없다.
- **6.7 B10 신규 벤치 추가 금지: 유지.** W7 범위 밖이라는 R1 합의를 철회할 근거가 없다.

## 4. 최종 권고

R2 후에도 Codex R1 입장은 모두 유지한다.

- 6.3은 다수안(JSON)으로 수렴하지 않고 **하드코드 `LensSkuRegistry`**를 계속 권고한다.
- 6.5는 Gemini 9/10 완화안을 채택하지 않고 **10/10 엄수 + 실패 SKU 개별 메타 fallback**을 계속 권고한다.
- 나머지 5개 합의 쟁점은 철회 논거가 없으므로 유지한다.
