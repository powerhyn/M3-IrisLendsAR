  - **버전 고정:** JSON 파일도 git 체크인 → 버전 고정 효과 동일.
  - **default fallback:** 메타 로더에 누락 SKU는 모든 플래그 `false` 기본값 (§6.4 WARN 로그 병행).

### 6.5 9/10 vs 10/10 — **10/10 엄수 채택 (Codex+Claude 다수)**
- Codex, Claude: **10/10 엄수** (R4 실기기 증거).
- Gemini: 9/10 완화 (실기기 노이즈 우려).
- **판정:** **실기기 R4 결과 "10/10 달성"이 팩트로 확인**된 상태. Gemini의 "실기기 노이즈 우려"는 이론적 가능성인데 R4 실측이 이를 기각.
- **완화 조항 (Gemini 우려 흡수):**
  - 배포 후 특정 디바이스에서 "자동감지 실패 1/N" 발견 시, **해당 SKU만 `has_baked_limbal: true` 메타 플래그로 명시 fallback**.

## R2.2 핵심 변화: 6.5 만장일치로 강화

- **Gemini가 9/10 완화안 명시 철회 → 10/10 엄수 선회.** 근거: R4 실기기 전수 통과 팩트가 이론적 노이즈 우려를 기각, 정책 일관성, JSON 메타 fallback이 이미 안전망이므로 임계값 낮춰 false positive 유발할 이유 없음.

## R2.3 남은 분기점: 6.3 메타 저장 (2/3 JSON, Codex 소수 고수)

R2에서도 6.3은 좁혀지지 않음. 양측 논거를 정직하게 기록한다.

**JSON 다수안 (Gemini + Claude):**
- 림발 플래그는 엔진 로직이 아니라 '에셋 프로파일'. 에셋 추가마다 SDK 재빌드는 비효율.
- 디자이너/QA가 `lens_meta.json`만 수정해 실기기 즉시 확인 → 생산성.
- git 체크인으로 버전 고정은 코드 방식과 동일 수준 보장.

**하드코드 레지스트리 (Codex 소수, 유지):**
- `has_baked_limbal`/`prefers_graphic_outline`/`prefers_crl`는 **렌더링 동작에 직결되는 정책 필드**. 이를 외부 JSON으로 여는 것은 "데이터 편집"이 아니라 "렌더링 정책 변경 채널을 하나 더 여는 것".
- JSON 완화책(git+default false+WARN)은 "깨지지 않게"만 할 뿐 "잘못된 정책이 안 들어가게"는 못함. 런타임 로더/파서/스키마/패키징이라는 **새 실패면** 추가.
- SKU 20개 규모에선 재빌드 회피 이익 < 정책 변경 blast radius 비용.

**Claude R2 보강 (양측 교량):** JSON 우선하되, SDK 공용 JSON 파서가 없어 경량 파서를 200줄 넘게 새로 짜야 하면 그땐 20개 하드코드 레지스트리가 합리적 폴백. → "JSON 우선, 파서 비용 크면 하드코드"라는 객관적 트리거.

**추가 고려(브레인스토밍 외 사실):** W7 §5.8 + `P6_implementation_handoff.md §4.5`에 따르면 `lens_meta.json`은 **W5와 공유 파일**(스키마 3필드, `prefers_crl` 포함)로 이미 규약됨. 하드코드를 택하면 W5 JSON + W7 하드코드로 메타 소스가 이원화 → SDK surface 일관성 저하 우려. **이 사실은 JSON 쪽 손을 들어줌** (단, W5 구현/파일 실재 여부는 미확인 — 현재 `lens_meta.json` 미존재).
