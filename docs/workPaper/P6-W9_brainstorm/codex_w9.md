# P6-W9 브레인스토밍 — Codex 의견

대상: `docs/workPaper/P6-W9_integration.md` §6.1 ~ §6.7

전제: W9는 새 설계 확장 단계가 아니라, Phase 6 결과를 안전하게 통합하고 `develop` 머지 리스크를 줄이는 경량 리뷰 단계로 본다.

## 6.1 머지 방식 (A/B/C)

- 추천: **옵션 A (merge commit)**.
- 근거: Phase 6는 W별 벤치와 판정 히스토리 자체가 의미 있으므로 squash나 rebase보다 원형 보존 가치가 크다. W3-04 정리 충돌도 merge 기록이 남아야 추적이 쉽다.

## 6.2 Android demo UI 정리 범위

- 추천: **W9 머지 범위에서 제외하고 별도 cleanup PR로 분리**.
- 근거: W9는 통합 검증과 머지 안정성이 우선이라 UI 정리까지 섞으면 diff만 넓어진다. deprecated 정리와 함께 Phase 7 초반에 묶는 편이 더 안전하다.

## 6.3 deprecated no-op 함수 완전 제거 시점

- 추천: **W9 머지에는 유지하고, `develop` 안착 후 Phase 7 초반 별도 PR에서 제거**.
- 근거: 지금은 no-op라도 통합 직전 호환 완충재 역할을 한다. 기능 머지와 API 제거를 한 PR에 섞으면 회귀 원인 분리가 어려워진다.

## 6.4 W9 브레인스토밍 필수 여부

- 추천: **필수 단계로 강제하진 말고, 1라운드 경량 리뷰만 권장**.
- 근거: W9의 목적은 새 쟁점 발굴이 아니라 W1~W8과 `99_final_decision.md` 정합성 확인이다. 이 정도 리뷰면 충분하고, 실제로 문서상 미닫힘도 이 수준에서 잡힌다.

## 6.5 성능 벤치 자동화

- 추천: **기존 FPS/타이밍 측정 경로를 재사용하고, 없으면 최소 frame counter + timer만 추가**.
- 근거: W9에서 새 자동화 프레임워크를 얹는 것은 통합 단계치고 비용이 크다. 회귀 비교에 필요한 최소 지표만 남기는 편이 목적에 맞다.

## 6.6 릴리즈 노트 작성

- 추천: **Phase 6 단일 릴리즈 노트 1장으로 묶고, W별 결정과 벤치 결과만 요약**.
- 근거: 최종 머지 뒤 참조점이 하나여야 `99_final_decision.md`, W 문서, PR 설명이 서로 어긋나지 않는다. W8 조건부 여부와 이월 항목도 여기서 한 번만 못박는 편이 낫다.

## 6.7 CI 통과 확인 항목

- 추천: **C++ 빌드, 단위 테스트, Android demo APK 빌드, 그리고 이미 연결된 정적 분석/린트만 필수로 본다**.
- 근거: W9 CI의 목적은 배포 경로가 깨지지 않았음을 확인하는 것이지 새 게이트를 늘리는 것이 아니다. 성능 벤치와 실기기 평가는 CI 조건이 아니라 통합 리포트로 분리하는 편이 맞다.

## Phase 6 간단 점검 (W1~W8 vs `99_final_decision.md`)

- 점검 결과: **전반적으로 일치한다**. W2~W8의 주요 결정 방향과 W4 B2 → W8 조건부 착수 체인은 `99_final_decision.md`와 문서상 같은 축으로 닫혀 있다.
- 놓친 부분: **W1 §6.2 ROI 마스크 반경(0.55/0.60/0.65)** 이 아직 `실기기 이관`으로 남아 있다. 새 쟁점은 아니고 기존 이관 항목이므로, W9 통합 리포트나 최종 상태표에 closure 상태를 명시하는 정도면 충분하다.
- 명칭 메모: `99_final_decision.md`에 적힌 조건부 pupil 트랙의 옛 이름 `P6-W1`은 Phase 6 문서에서 `P6-W8`로 재배치돼 있다. 이름만 이동한 것이고 결정 내용 자체의 불일치는 아니다.
