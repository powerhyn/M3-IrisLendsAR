## 0. 세 줄 요약

1. **원인은 링 FBO 치수 전치다.** 카메라가 주는 버퍼는 세로형인데 링/렌즈 FBO를 `SurfaceRequest.resolution`(센서 좌표 1920×1080) 그대로 잡아, OES→링 패스가 **장면 가로축 표본을 1920→1080으로 43% 소거**한다.
2. **화면에서는 왜곡으로 안 보인다.** 최종 blit의 Cover 계산이 `isRotated`로 치수를 되교환해(실측 배율 x2.85 / y0.90 = 3.17배) 링의 비등방 3.03배를 상쇄한다. 그래서 종횡비는 맞고 **가로 뭉개짐**으로만 나타난다.
3. **처방을 실측 검증했다.** 링 FBO를 실제 콘텐츠 치수로 잡으면 **가로 고주파가 2.73배 복구**되고(1.227→3.346) 세로는 불변, 가로/세로 비가 0.221→0.612로 **FMLens(0.634)와 일치**한다. 화면 기하도 정상 유지.

## 3. 핵심 실측 — 축별 배율과 비등방

추론 대신 **정합(registration)** 으로 확정했다.

### 3-1. 링 FBO → 화면 매핑 (최종 blit 실효 배율)

링 덤프를 (회전, mag_x, mag_y)로 리샘플해 화면 캡처와 FFT 정규화 상호상관.

| | 값 |
|---|---|
| 최적 NCC | **0.9948** (사실상 완전 일치) |
| mag_x | **2.850** |
| mag_y | **0.900** |
| 비등방비 | **3.167** |

코드 독해 예측(2.816 / 0.891)과 탐색 격자 오차 내에서 일치한다.

### 3-2. 링 FBO → FMLens 화면 (기하 기준) 정합

FMLens는 정사각 1440×1440 소스를 하드웨어 스케일러로 ×1.80 **등방** 확대하므로 화면 기하를 기준으로 쓸 수 있다. 같은 태블릿·같은 벽면.

| | 값 |
|---|---|
| 최적 NCC | 0.8603 |
| mag_x | **2.700** |
| mag_y | **0.890** |
| 비등방비 | **3.034** |

→ **링 FBO 내용 자체가 이미 3.03배 비등방이다.** 화면이 멀쩡해 보이는 이유는 blit의 3.17배가 이를 상쇄하기 때문이다.

### 3-3. 여기서 나오는 기하 결론

세 측정을 맞추면 카메라가 실제로 주는 OES 버퍼는 **1080×1920(세로형)** 이다:

- 그 버퍼를 1080×1920으로 보면 화면 배율이 x ≈1.58 / y ≈1.52 로 **등방**이 된다.
- 반면 1920×1080으로 잡으면 정확히 관측된 3.0~3.2배 비등방이 나온다.
- 4-2의 처방 검증(전치 보정 시 가로 복구)이 이 결론을 독립적으로 재확인한다.

`targetRotation = Surface.ROTATION_0` 핀 + 태블릿 natural orientation이 세로(landscape에서 `Screen rotation → 90`)인 조합의 결과다. 그런데 `SurfaceRequest.resolution`은 **센서 좌표** 1920×1080을 보고하고, `CameraGLView.fulfillPendingSurfaceRequest()`가 그 값을 그대로 `setFrameSize()`에 넘긴다.

## 4. 선명도 정량 — 축을 분리해야 보인다

선행 문서 §2는 등방 라플라시안 분산만 봤다. 배율이 축마다 갈리므로 **가로/세로 2차차분 분산을 분리**해야 손실 위치가 드러난다.

### 4-1. 기준선 (같은 벽면, 순수 타일면 ROI)

ROI `x 1950–2550, y 300–1400` (선행 문서와 동일):

| | 라플라시안 | 가로 2차 | 세로 2차 | 가로/세로 | 평균밝기 |
|---|---|---|---|---|---|
| IrisLens | 5.616 | **0.857** | 3.528 | **0.243** | 141.4 |
| FMLens | 7.333 | **2.162** | 3.413 | **0.634** | 149.8 |

ROI `x 1450–1950, y 1150–1500` (더 평탄한 타일면):

| | 라플라시안 | 가로 2차 | 세로 2차 | 가로/세로 |
|---|---|---|---|---|
| IrisLens | 2.247 | 0.563 | 0.909 | 0.620 |
| FMLens | 3.033 | 0.927 | 1.087 | 0.854 |

**해석 — 이게 지문이다.**
- **세로 고주파는 FMLens와 동등**(3.528 vs 3.413 = 1.03배).
- **가로만 2.52배 열세**(0.857 vs 2.162).
- 손실이 한 축에만 몰려 있다 = 비등방 리샘플. 카메라 HAL 차이나 전역 흐림이라면 두 축이 같이 내려간다.

### 4-2. 처방 검증 — 링 FBO 전치 보정 A/B

링/렌즈 FBO를 회전 시 실제 콘텐츠 치수로 잡고 blit의 이중 교환을 제거한 진단 토글(기본 OFF)로 같은 장면 A/B:

| | 라플라시안 | 가로 2차 | 세로 2차 | 가로/세로 | 평균밝기 |
|---|---|---|---|---|---|
| OFF (현행) | 8.626 | **1.227** | 5.552 | **0.221** | 206.4 |
| ON (보정) | 11.699 | **3.346** | 5.466 | **0.612** | 212.3 |
| FMLens 참고 | — | — | — | **0.634** | 219.0 |

- **가로 고주파 2.73배 복구**, 세로 불변(5.55→5.47) — 예측과 정확히 일치.
- 가로/세로 비가 **FMLens와 사실상 동일**(0.612 vs 0.634)해진다.
- 링 덤프 파일명이 `ring_1080x1920_...`로 바뀌고, **화면 기하는 정상 유지**(안경 원형·얼굴 비례 정상, 육안 확인).
- 계산상 blit이 등방 **×1.584**가 된다 — 선행 문서 §3이 가정했던 1.58과 일치.

### 4-3. 선행 문서 §6-5 보조 카드 — 언샤프는 답이 아니다

동일 ROI, 평균밝기 ~196 조건:

| 모드 | 라플라시안 | 가로 2차 | 세로 2차 |
|---|---|---|---|
| 0 bilinear | 14.380 | 3.290 | 8.066 |
| 1 bicubic (현행 기본) | 8.960 | 1.188 | 5.943 |
| 2 bicubic + 언샤프 | 9.331 | 1.326 | 6.056 |

- **언샤프(mode 2)는 mode 1 대비 +4%에 그친다.** 4.4배 격차를 메우지 못한다 → 보조 카드 폐기.
- ⚠️ **지표 함정 기록**: bilinear(mode 0)이 수치상 가장 높지만 이는 확대 구간에서 bilinear이 만드는 **조각선형 계단 아티팩트**가 2차차분을 부풀린 것이지 디테일 복원이 아니다. 보간 커널 비교에 라플라시안 분산을 쓰면 안 된다. 이 축은 육안 판정으로만 결정할 것.

## 5. 확정된 원인 (한 문단)

`CameraGLView.fulfillPendingSurfaceRequest()`가 `SurfaceRequest.resolution`(센서 좌표 **1920×1080**)을 그대로 `setFrameSize()`에 넘겨, 링/렌즈 FBO가 1920×1080으로 할당된다. 그러나 `targetRotation=ROTATION_0` 핀 + 태블릿 natural=세로 조합에서 카메라가 실제로 채우는 버퍼는 **1080×1920**이다. `stMatrix`가 항등이라 OES [0,1]² → 링 [0,1]² 매핑이 그대로 일어나므로, 이 치수 불일치가 곧 **전치 리샘플**이 된다 — 장면 가로축은 1920→1080으로 표본이 소거되고(되돌릴 수 없음), 세로축은 1080→1920으로 무의미하게 증폭된다. 최종 blit의 Cover 계산이 `isRotated`로 치수를 되교환해 종횡비만 복원하므로 화면에서는 왜곡이 아니라 **가로 방향 뭉개짐**으로만 드러난다.

선행 문서 §5의 직관("회전과 버퍼 치수 불일치 → 압축·복원 왕복 손실")은 **방향이 옳았고**, 다만 기전이 `stMatrix` 회전이 아니라 `SurfaceRequest.resolution` 좌표계 오해였다.

## 7. 본수정 (브랜치 `fix/ring-fbo-transpose`)

### 7-1. 무엇을 고쳤나

**`ringW`/`ringH`를 링 공간의 단일 진리원으로 승격**하고, 회전 90/270이면 요청 치수를 교환해 링/렌즈 FBO를 **항상 콘텐츠 실치수**로 잡는다. 링이 upright 실치수가 되므로 `renderToScreen`의 되교환(`isRotated`)을 제거하고, native 렌즈/뷰티에 넘기던 텍스처 치수를 `frameWidth/frameHeight`(센서 좌표) → `ringW/ringH`(실제 FBO)로 바꿨다.

**회전 정본 생산자를 바꿨다.** 종전에는 `frameRotation`을 ImageAnalysis의 `imageInfo.rotationDegrees`에서만 얻었는데, 그 값이 링 치수를 결정하게 되면서 두 결함이 생긴다: (a) 프리뷰 surface보다 **348ms 늦게** 도착하고 (b) `EXPERIMENT_PREVIEW_ONLY`처럼 ImageAnalysis를 안 묶는 경로에선 **아예 오지 않아** 링이 전치 상태로 고착된다. `SurfaceRequest.setTransformationInfoListener`로 **프리뷰 자신의 회전**을 받아 둘 다 해소했다. 순서는 '보장'하지 않고 `setFrameRotation`의 **멱등 재생성**(계산 치수가 실제로 바뀔 때만)으로 자가 치유한다.

실측 확정값 (SM-X920, 2026-07-29):

| 값 | 실측 | 비고 |
|---|---|---|
| `TransformationInfo.rotationDegrees` | **270**, `hasCameraTransform=true` | surface 콜백과 **같은 ms**에 도착 |
| `cameraInfo.sensorRotationDegrees` | **270** | bind 시점에 이미 확정, 위와 동일 |
| `imageInfo.rotationDegrees` | 270 | 321ms 늦게 도착 → 이제 변경 가드에 걸려 no-op |
| 분석 버퍼 실치수 | **512×288** (요청 960×540에서 폴백) | rot270 스왑 → upright 288×512 = 0.5625 = 링 종횡비와 일치 ✓ |
| `frameRotation` (화면을 세로로 돌린 뒤) | **270 불변** | 화면 방향과 무관 — `targetRotation` 핀의 결과 |

### 7-2. 검토에서 뒤집힌 것 (재조사 금지)

멀티에이전트 매핑(5영역 108건) + 적대 검증 3관점 결과 중 **직접 확인해 사실로 확정**한 것:

| 이전 계획/문서의 서술 | 판정 | 근거 |
|---|---|---|
| "`resolveCoordinateSpace` 동반 조정 필수" | **해당 없음** | 호출자 0건. 렌즈 좌표는 native가 `IrisResult.frame_width/height`로 직접 계산(`uFrameAspect`) |
| "`createLensFbo`가 렌즈 출력을 담당" | **도달 불가(dead)** | `lensFboId`는 그 함수 안에서만 non-zero인데 유일 호출처가 `if (lensFboId != 0)` 가드. 실제 출력은 native `TexturePool` |
| "치수 인자가 틀리면 렌즈가 타원이 된다" | **거짓** | 렌즈 기하는 전부 UV 공간이라 픽셀 치수와 독립. 틀리면 **타원이 아니라 선명도로만** 드러난다 — 게이트 설계의 함정 |
| "`OverlayView`는 `displayZoom`을 모른다" | **거짓** | `OverlayView.kt:656`이 곱한다. Activity가 GL과 Overlay 양쪽에 동일 주입 |
| "폰 세로 고정이면 `frameRotation=0`이라 무회귀" | **성립 불가 가능성 높음** | `targetRotation=ROTATION_0` 핀이라 화면 방향과 무관. 태블릿에서 화면을 세로로 돌려도 270 불변. 폰도 270이면 **무회귀가 아니라 동일 개선**이다 — 폰 실측 전까지 '무회귀'라고 쓰지 말 것 |

### 7-3b. G8 — 폰 실측 (SM-S916N / Galaxy S23+, Android 16, 세로 회전 잠금)

**"폰 세로 고정이면 `frameRotation=0`이라 무회귀"는 거짓이었다.** 폰도 270이고 같은 전치
리샘플을 겪고 있었다.

```
sensorRotationDegrees=270, screenRot=0
TransformationInfo: rotationDegrees=270, hasCameraTransform=true, cropRect=(0,0-1920,1080)
stMatrix = 정확한 항등행렬                      ← 태블릿과 동일
Frame rotation set: 270 (prev=0)
Intermediate ring buffers created: 1080x1920 (req=1920x1080 rot=270 swapped=true)
Camera rotation (TASKS): 270, analysis buffer=640x360, screenRot=0   ← 642ms 늦게, no-op
```

**축 대응이 태블릿과 반대다.** 폰은 `screenRot=0`이라 `rotK=0`(blit 회전 없음)이므로,
구동작에서 소거되던 축이 태블릿의 '가로'가 아니라 **'세로'** 다. 그래서 벽면 ROI의
가로/세로 비 지문도 방향이 뒤집힌다(태블릿 구동작 0.28 / 폰 구동작 1.06~1.22).
**축 비를 기기 간에 그대로 비교하면 안 된다** — 화면 회전에 따라 어느 축이 손상되는지가 바뀐다.

## 8. 실측 재현 방법

### 진단 브로드캐스트 (디버그 빌드 전용)

```bash
ADB=~/Library/Android/sdk/platform-tools/adb
$ADB shell am broadcast -a com.irislenssdk.demo.DUMP_RING          # 링 FBO 원본 PNG 덤프
$ADB shell am broadcast -a com.irislenssdk.demo.SET_UPSCALE --ei mode 2
$ADB shell am broadcast -a com.irislenssdk.demo.SET_RING_SWAP --ez legacy true   # 구 전치 동작 복원(A/B)
$ADB pull /sdcard/Android/data/com.irislenssdk.demo/files/sharpdump/
```

화면을 만지지 않고 상태를 바꾸는 게 요점이다 — 태블릿이 흔들리면 장면이 바뀌어 A/B가 오염된다.

### 측정 스크립트

`axis_metrics.py`(축 분리 2차차분), `measure_mag.py`(축별 배율 정합), `ring_vs_fmlens.py`(기하 기준 정합).
※ 선행 문서 §8-A의 등방 라플라시안만으로는 이번 원인이 보이지 않는다. **반드시 축을 분리할 것.**

### 함정

- 태블릿 절전으로 화면이 꺼지면 `screencap`이 전부 검은 이미지를 낸다. 측정 전 `svc power stayon true`.
- 두 앱은 FOV가 달라 같은 ROI가 다른 피사체를 담는다. ROI는 **양쪽 모두 순수 벽면인지 눈으로 확인**할 것.
- 카메라 AE가 장면에 따라 크게 움직인다(평균밝기 124~219 관측). 밝기가 다른 캡처끼리 절대값 비교 금지.
