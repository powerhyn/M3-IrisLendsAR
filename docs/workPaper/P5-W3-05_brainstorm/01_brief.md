## 1. 제품 맥락

IrisLensSDK는 실시간 카메라 영상에서 홍채를 추적하여 **가상 컬러 컨택트 렌즈**를 오버레이하는 AR SDK입니다. 30fps 이상, 모바일 온디바이스.

**남은 두 개의 큰 과제**:
- (A) **렌즈 렌더링 자연스러움** ← 지금 다룸
- (B) 얼굴 일부만 보일 때 눈 추적 (별개 트랙)

**핵심 아키텍처 원칙**: 렌즈 렌더링과 홍채 트래킹은 **결합도를 최소화**해야 한다. 얼굴/눈 인식 모델은 TFLite 레이어에서 언제든 교체 가능해야 하고, 렌더러는 그 영향을 받지 않아야 한다. 따라서 렌더러의 입력 계약은 **"홍채 중심(정규화 좌표), 홍채 반경, 비대칭 타원(눈꺼풀/흰자 경계) 파라미터, 가시성/신뢰도"** 수준으로 고정하는 것이 바람직하다.

## 2. 현재 우리 구현 (As-Is)

파일: `cpp/src/gpu/shader_sources.cpp` 의 `LENS_OVERLAY_FRAGMENT` (GLES 3.1).

이미 들어가 있는 것 (Android 데모에서 검증 후 C++ 코어로 포팅 완료):

1. **비대칭 타원 마스크** (`asymmetricEllipseMask`)
   - 내안각/외안각 반경 분리(rxInner/rxOuter), 회전 포함.
   - 16점 contour에서 `fitEyeEllipse`로 피팅 → OneEuroFilter로 스무딩 → 5프레임 홀드 캐시.
2. **눈꺼풀 클리핑** — 타원 모드 또는 Y-slab 폴백.
3. **8종 블렌드 모드** — Normal, Multiply, Screen, Overlay, LuminanceTint, LuminanceTintLinear, SoftLight, ColorReplace.
   - 특히 LuminanceTintLinear: sRGB→Linear → 평균 휘도 스케일 → 실반사(spec>0.7) 보호 → sRGB 복귀.
4. **Sclera Protection** — 기하학적(`r>0.75`에서 smoothstep) + 색상 기반(`calcScleraFactor`: 밝기·채도로 흰자 감지).
5. **Contact Shadow** — 위 눈꺼풀 아래 4px 그림자. `uShadowIntensity` 제어, 눈감김 시 비활성화.
6. **Edge Feather** — 홍채 경계 페더링(`uEdgeFeather`).
7. **분석적 Normal Map + 라이팅** (W3-04, 2026-04-22 완료):
   - 홍채 로컬 좌표 `(adjustedCoord - adjustedCenter) / scaledRadius`에서 구면 노멀 계산.
   - Fixed light `vec3(0.3, 0.4, 1.0)` diffuse + specular(power 24).
   - `mix(1.0, lighting, finalAlpha)`로 렌즈 영역에만 마스킹. `uHighlightEnabled` 토글 (기본 OFF).
8. **림발 다크닝 코드는 존재하나 비활성** (`LIMBAL_ENABLED = false`) — 대부분의 렌즈 텍스처에 이미 림발이 포함되어 이중 적용 방지가 이유.
9. **Adreno mipmap 대책** — `dist >= 1.0` early return을 제거해서 dynamic branch 내 `texture()` gradient undefined 이슈 회피.

입력 좌표: `uLeftIrisCenter/Radius`, `uRightIrisCenter/Radius` (정규화), `uFrameAspect`, 타원 6파라미터, 눈꺼풀 top/bottom 등.

스무딩·프레임 제어·confidence 관리는 **W1 TemporalStabilizer**가 소유(동일 Phase에서 완료). 렌더러는 stabilized 좌표만 받는다.

## 4. 현재 결과물이 "어색한" 부분 (체감 정리)

1. **플랫한 느낌** — 분석적 노멀 ON에서도 아직 "구체"가 아니라 "살짝 기울어진 원"처럼 보일 가능성. 고정 조명이라 사용자 환경(실내/실외) 변화에 반응 안 함.
2. **홍채 디테일 유실** — Normal/Multiply에서 사용자 본인 홍채 무늬/동공 경계가 뭉개지거나 과하게 가려진다.
3. **동공 중심이 렌즈 중심과 안 맞는 경우** — 홍채 랜드마크가 동공 기준이 아닌 홍채 중심 기준이라 시차 생길 수 있음. 사용자가 측면을 보면 더 심함.
4. **경계가 너무 깔끔하거나(2D 스티커) 너무 흐림(페더링 과다)** — 림발 링이 없어서 구분이 모호.
5. **하이라이트 없음 or 있을 때 과함** — 실제 눈은 고개/조명 움직임에 따라 하이라이트 위치가 변해야 자연스러움.
6. **양쪽 눈 비대칭** — 좌우 조명 방향이 같이 움직여야 하는데 고정되어 있음.
7. **블링크/움직임 전환 시 플리커 가능성** — W1에서 스무딩은 되지만 렌더러 레벨에서 부드러운 페이드가 필요할 수 있음.

## 5. 질문 축 (각 축별로 아이디어 1개 이상 주세요)

### 축 A: 광학 리얼리즘 (3D 곡면감·반사·굴절)
- IBL을 추가한다면 HDR vs LDR, 풀 환경맵 vs 스크린스페이스 반사 vs 카메라 프레임 자체를 환경맵처럼 샘플링?
- 분석적 노멀 유지 vs 사전 베이크 텍스처 노멀 vs 런타임 치환?

- 동공(pupil) 별도 렌더 레이어 필요 여부.

### 축 B: 컬러 블렌딩 — **최종 4개 이하로 정리** (최우선 질문)

**배경**: 현재 8종 블렌드 모드는 선택지가 너무 많아서 실제 프로덕트에서 SKU별로 "어떤 걸 써야 하지?" 판단이 어렵다. 사용자가 마주하게 될 **렌즈 타입 다양성(컬러감·밝기·불투명도)을 최소 개수로 커버**할 수 있는 **4종 이하**(2~4개)의 최종 세트를 제안해달라.

**접근 자유**: 기존 8종 중에서 추리기 / 기존에 없는 신규 블렌드 추가 / 기존 1~2개를 신규 블렌드로 대체 / 조합 — 어느 쪽이든 근거만 있으면 OK. 원론적으로 "더 나은 블렌드"가 있다면 주저 없이 제안해달라.

**현재 8종 요약 (`LENS_OVERLAY_FRAGMENT`의 `blend*` 함수)**:

| ID | 이름 | 수식 요약 | 강점 | 약점 |
|----|------|----------|------|------|
| 0 | Normal | `mix(base, blend, a)` | 단순·예측가능, 짙은 불투명 서클렌즈 OK | 디테일·음영 무시, 평면적 |
| 1 | Multiply | `base * blend` | 짙은 색(갈색/블랙) 자연스러움 | 밝은 렌즈색은 묻힘 |
| 2 | Screen | `1-(1-base)(1-blend)` | 밝은 톤(헤이즐/그레이/밝은블루) 살아남 | 짙은 렌즈는 거의 무효 |
| 3 | Overlay | Multiply+Screen 하이브리드 | 대비 강화 | 과장되기 쉬움, 동공 영역 이상해짐 |
| 4 | LuminanceTint | 베이스 휘도 × 렌즈색 | 휘도 구조 보존, 디테일 살음 | sRGB 감마에서 계산돼 색 정확도 낮음 |
| 5 | **LuminanceTintLinear** | 선형공간 휘도 스케일 + 실반사(spec>0.7) 보호 | 가장 "자연스러운" 후보. 디테일·하이라이트 모두 보호 | 계산량 약간 ↑ |
| 6 | SoftLight | Overlay보다 부드러운 대비 | 은은한 보정 | 색 변화 약해서 진한 렌즈 티 안 남 |
| 7 | ColorReplace | 베이스 밝기로 렌즈색 재스케일 (detail 약함) | 불투명 렌즈 색 정확도 최고 | 원본 디테일 거의 날아감 |

**압축 기준 (커버해야 할 "렌즈 타입 × 사용자 홍채" 매트릭스)**:
- 렌즈 컬러감: 짙은(다크 브라운·블랙) / 중간(헤이즐·올리브) / 밝은(그레이·블루·바이올렛) / 화이트/투명톤
- 렌즈 불투명도: 반투명 자연렌즈 / 불투명 서클렌즈 / 무늬·그라디언트 렌즈
- 사용자 홍채: 짙은 홍채(렌즈색 안 올라감) / 밝은 홍채(렌즈색 쉽게 덮임)

**원하는 답**:
1. **최종 세트** (n ≤ 4): 이름 + 수식/한 줄 의사코드 + 각 모드가 매트릭스의 어느 칸을 커버하는지 명시. 기존 재사용이면 ID를 쓰고, 신규면 이름을 붙여달라.
2. **드롭 목록**: 기존 8종 중 빼는 것 + 이유 (예: "SoftLight는 Normal과 체감 차이가 거의 없어서 드롭", "ColorReplace는 LuminanceTintLinear의 상위호환에 흡수됨").
3. **신규 추가/대체 (선택)**: 기존에 없던 블렌드를 추가한다면 근거 (Perfect 24+에 있을 법한 기법, 포토샵/Pegtop Soft Light 등 표준 합성식, 렌즈 도메인 특화 공식 등). GLSL 한 줄로 기술 가능한 수준이 이상적.
4. **기본값 1개 추천**: 4종 중 UI에서 디폴트로 노출할 1종 + 이유.

### 축 B-보조: 홍채 디테일 보존 (블렌드 압축과 별개 질문)
- 사용자 원본 홍채의 detail(무늬·방사 스트럭처)을 blend 후에도 살리는 방법. detail layer 분리 후 재주입?
- Pattern × Palette 모델 도입 시 렌더러 API 영향. 단일 PNG 호환 유지 가능한가?

### 축 C: 경계·마스킹 (림발·눈꺼풀·속눈썹·흰자 노이즈)
- 림발 링을 **텍스처 내 포함** vs **셰이더에서 합성**, 어느 쪽을 default로? 텍스처가 이미 가진 경우의 이중적용 방지 전략.
- 속눈썹 가림 — 현재 없음. 눈꺼풀 마스크로 충분한지, 별도 속눈썹 알파 패스가 필요한지.
- 흰자 번짐 방지(sclera protect) 현재 방식의 취약점 및 개선.
- 동공-홍채 경계에서의 feather.

### 축 D: 시간적 안정성 (플리커·스냅)
- W1이 좌표를 안정화하지만, 렌더러 쪽에서 추가로 해야 할 것이 있나? (alpha hysteresis, lighting parameter smoothing 등)
- 블링크 시 렌즈 페이드 전략 (즉시 off vs 부드러운 alpha 감소).
- 얼굴 검출 실패 몇 프레임까지 이전 좌표로 렌더링 유지?

### 축 E: 입력 계약 (렌더러 ↔ 검출기 결합도)
- 현재 입력 계약을 어떻게 정의하면 **검출 모델을 자유롭게 바꿔도** 렌더러가 동일하게 동작할까? 추가로 필요한 필드(pupil center, gaze vector, eye_depth_mm, head_pose 등) 중 "선택적"으로만 노출해야 할 것은?
- 검출 실패 시 폴백 정책을 렌더러가 소유해야 하는지, 아니면 상위에서 null을 보내는지.

### 축 F: 성능/타이밍
- 저~중급 안드로이드에서 30fps 유지하는 선에서 IBL/추가 노멀맵/pass 추가 여유가 얼마나 있나?
- 추가 pass가 필요한 기법과 single-pass로 욱여넣을 수 있는 기법 구분.
- Adreno/Mali 각각의 주의점 (특히 mipmap + dynamic branch 이슈 같은 것).

### 축 G: "아예 다른 접근" (와일드카드)
- 3D Face Geometry를 다시 고려할 가치가 있는지?
- Neural rendering (e.g., 작은 Super-res on eye region, learned harmonization) 검토 가치?
- 렌즈 텍스처 자체를 프로시저럴 생성(셰이더에서 절차적 홍채)으로 바꿀 가치?
- 기타 비주류 아이디어 환영.

## 6. 제약·전제

- **타겟 FPS**: 30fps 이상 (MID tier 기준), 60fps 가능하면 이상적.
- **APK 증가 허용치**: ~1~2MB 내. HDR 에셋도 이 범위면 가능.
- **플랫폼 우선순위**: Android 먼저. iOS/Flutter/Web로 이식 가능한 설계여야 함 (OpenGL ES 3.1 또는 Metal 상응 가능).
- **렌즈 텍스처 호환**: 기존 단일 PNG 입력은 유지하되, Pattern/Palette 모델로 확장 여지가 있어야 함.
- **API 호환**: C API (`iris_sdk_render_lens`) 기존 시그니처는 가능한 유지. 새 파라미터는 opt-in 구조여야 함.

## 9. 멀티라운드 수렴 프로세스

이 브레인스토밍은 **여러 라운드**로 진행됩니다. 각 라운드의 목적이 다르니 혼동하지 마세요.

### 라운드 1 (R1) — 독립 응답 (지금 이 브리프)

- Codex, Gemini, Claude가 서로를 보지 않고 **독립적으로** 섹션 7 템플릿에 따라 응답.
- 출력: `codex_response.md`, `gemini_response.md`, `claude_response.md` (각자 자기 파일만 작성)
- 목표: 서로 다른 시각에서 가설·결론을 **편향 없이** 추출.

### 라운드 2 (R2) — 교차 비판

- Claude가 R1의 세 응답을 읽고 **쟁점 목록(issue list)**을 추출해서 `r2_issues.md`로 공유.
  - 합의된 것(closed): 세 모델이 같은 결론 → 최종 채택 목록에 바로 추가, 더 논의 안 함
  - 갈린 것(open): 모델마다 다른 결론 → **쟁점별로 추천/기각 논리를 정면 충돌시킴**
- Codex와 Gemini는 `r2_issues.md`를 읽고, **자기 R1과 다른 결론을 낸 상대 모델의 논리를 구체적으로 반박**하거나 **설득당했다면 왜 설득당했는지** 명시.
  - 출력: `codex_r2.md`, `gemini_r2.md`
  - "둘 다 일리 있다"식 얼버무림 금지. 반박하거나 입장 변경하거나 둘 중 하나.
- Claude도 동일하게 `claude_r2.md` 작성.

### 라운드 3 (R3, 필요 시) — 쟁점 수렴 재질문

- R2 이후에도 갈리는 쟁점만 추출해서 Claude가 **파고드는 specific 질문**을 각 모델에 개별로 던짐 ("Gemini가 IBL 도입에 찬성한 근거 X에 대해 Codex가 추가로 답해달라" 같은 타겟팅).
- 실험 돌려서 확정 가능한 것(예: "Normal vs LuminanceTintLinear 체감 차이 벤치")은 **실험 제안 + 예상 결과**를 요구.
- 출력: 라운드·쟁점별 단편 응답. Claude가 `final_decision.md`에 정리.

### 수렴 규칙

1. **합의된 것은 빨리 닫는다.** 세 모델이 같은 결론이면 R2에서 재논의 금지.
2. **어중간한 타협 금지.** 대립 의견은 대립한 채로 근거 대결. 타협안은 쟁점을 은폐할 뿐이다.
3. **실기기로 판정 가능한 쟁점은 실기기로 넘긴다.** 말로 안 끝나면 "이 벤치로 확정" 제안.
4. **라운드 수는 고정하지 않는다.** 쟁점이 다 닫히면 조기 종료. 5라운드 가도 무방.

### Claude의 역할 (모더레이터)

- R2에서 쟁점 목록 작성, 양쪽 논리 정리, 숨겨진 합의/대립 지점 발굴.
- R3에서 타겟팅 질문 생성.
- 최종 `final_decision.md` 작성 (축별 결론 + 실행 순서 + Phase 6로 미루는 것).
- 이 역할 때문에 Claude의 R1 응답은 Codex/Gemini보다 **덜 단정적**으로 써도 됨 (대신 R2에서 판정자 역할 강화).
