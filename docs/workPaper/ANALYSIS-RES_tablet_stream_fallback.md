# ANALYSIS-RES — 태블릿 분석 스트림이 512×288로 떨어지는 원인과 해소

> 상태: **✅ 원인 확정 · ⏸ 상향 판정은 렌즈 렌더링 트랙으로 이월** — 기본값은 960×540(=태블릿 512×288) 유지
> 브랜치: `develop` 직접 (SHARP/TRACK-ROT 종결 후 착수)
> 선행: `TRACK-ROT_landscape_hint_mismatch.md` §5-3 이 "다음 후보"로 지목한 항목
> 실측: 2026-07-31 / SM-X920 (Tab S10 Ultra) — 폰 SM-S916N 은 무선 adb 이탈로 미대조

---

## 0. 세 줄 요약

1. **요청값이 어느 기기에서도 지원되지 않는 값이었다.** 앱은 분석 스트림에 `960×540` 16:9를 요청하는데, 실측한 두 기기 **모두 그 크기를 지원하지 않는다.** 실제 크기는 폴백 규칙이 기기별 지원 목록에서 고른 값이다.
2. **태블릿은 960×540 아래에 512×288 밖에 없다.** 그래서 폰(640×360)의 **1/1.56 면적**으로 떨어졌다. 규칙대로 동작한 것이지 버그가 아니다.
3. **요청을 실재하는 값 `1280×720`으로 올린다.** 두 기기 모두 지원하므로 폴백이 기기별로 갈리지 않는다. 단 면적이 태블릿 6.25배·폰 4배라 비용 검증이 필요하다.

## 1. 원인 — dumpsys 실측

`adb shell dumpsys media.camera` 의 `android.scaler.availableStreamConfigurations`
(포맷 35 = `YUV_420_888`, ImageAnalysis 가 실제로 여는 포맷) 파싱 결과.

**SM-X920 전면 카메라 (internal/1, internal/3 동일) — 16:9 전체 목록**

```
4000x2252   3840x2160   1920x1080   1280x720   512x288
```

- `960×540` **미지원**
- `640×360` **미지원** ← 폰의 값을 그대로 옮기는 것은 이 기기에서 불가능하다
- 1280×720 과 512×288 **사이가 통째로 비어 있다**

앱 설정 (`GpuRenderActivity.kt`):

```kotlin
selectAnalysisResolution() → Size(960, 540)                       // 요청
ResolutionStrategy(size, FALLBACK_RULE_CLOSEST_LOWER_THEN_HIGHER) // 폴백 규칙
AspectRatioStrategy.RATIO_16_9_FALLBACK_AUTO_STRATEGY             // 16:9 강제
```

→ "16:9 중 960×540 이하에서 가장 가까운 것" = **512×288**. 규칙대로다.

**직접 증거**: 앱 실행 중 dumpsys 의 소비자 목록에
`Consumer name: ImageReader-512x288f23m4-28173-0` (pid 28173 = 데모 앱, f23 = YUV_420_888).

## 2. 왜 이게 랜드마크 정밀도에 불리한가

코드 주석에는 "FaceLandmarker 는 내부에서 자체 입력 크기로 리사이즈하므로 고해상 프레임은
이득이 없다"고 적혀 있었으나, **부분적으로만 맞다.**

FaceLandmarker 는 2단계다:
1. **검출(BlazeFace)** — 다운스케일된 전체 프레임에서 얼굴 박스를 찾는다. 이 단계는 소스
   해상도에 둔감한 게 맞다.
2. **랜드마크** — 검출된 박스로 **원본에서 얼굴 ROI 를 크롭**해 모델 입력 크기로 리사이즈한다.
   **이 단계는 소스 해상도에 직접 민감하다.**

얼굴이 프레임의 1/4 폭을 차지한다고 하면:
- 512×288 → ROI 크롭 ≈ 128×144 → 모델 입력으로 **업스케일** (없는 디테일을 만들어 냄)
- 1280×720 → ROI 크롭 ≈ 320×360 → **다운스케일** (디테일 보존)

태블릿은 화면이 커서 폰보다 **멀리 두고 쓰므로 얼굴이 프레임에서 더 작게 잡힌다** —
같은 512×288 이라도 태블릿 쪽이 더 불리하다.

> ⚠️ 위 문단은 모델 구조에서 나온 **추론**이다. 실제 개선 폭은 육안 판정으로 확인할 것.
> 정량 지표는 TRACK-ROT §3-3 전례(정지 상태 마커 흔들림 = 판별력 없음)를 반복하지 말 것.

## 3. 시도한 수정과 그 결과

```kotlin
// selectAnalysisResolution(), USE_16_9_CAPTURE 경로 — 시험 적용 후 되돌림
- if (totalRamMb <= 3072) Size(640, 360) else Size(960, 540)
+ if (totalRamMb <= 3072) Size(640, 360) else Size(1280, 720)
```

`1280×720` 을 고른 이유: **두 기기 모두 실재하는 16:9 값**이라 폴백이 기기별로 갈리지 않는다.
16:9 를 유지하는 한(프리뷰와 종횡비가 같아야 랜드마크 정규화 좌표가 렌더 텍스처에 대응)
512×288 위의 선택지는 이것 하나뿐이다 — **두 값 사이에 중간이 없다.**

**비용**: 면적 태블릿 **6.25배**(147,456 → 921,600 px), 폰 4배. 프레임당 RGBA 는
590KB → 3.7MB. 30fps 기준 대역폭 17MB/s → 110MB/s.

**→ 기본값은 960×540 으로 되돌렸다.** 기각이 아니라 **판정 이월**이다 (§6).

## 4. 검증할 것 (게이트)

| 게이트 | 기대 | 결과 |
|---|---|---|
| **A1 바인딩** | `No supported surface combination` 없이 바인드 성공 | ✅ 실패 로그 0건 |
| **A2 실제 크기** | `analysis buffer=1280x720` | ✅ `analysis buffer=1280x720` + dumpsys `ImageReader-1280x720f23m4` |
| **A3 Detect FPS** | 30 유지 (종전 30~31) | ❌ **24~27** (3회 표본 27/26/24) |
| **A4 Render FPS** | 60 유지 | ✅ 59~61 |
| **A5 추론 지연** | 종전 대비 악화 폭 | ⚠️ **26~35ms** (종전 얼굴無 ≈21ms) |
| **A6 랜드마크 육안** | 마커 밀착도·고개 돌릴 때 안정성 개선 체감 | ⏳ **사용자 판정 필요** |
| **A7 폰 무회귀** | 폰도 1280×720 으로 올라가며 fps 유지 | ⏳ (adb 재연결 필요) |

### A3/A5 측정 조건과 해석 — ⚠️ 아직 결론 내지 말 것

위 수치는 **얼굴이 프레임에 없는 상태**(천장을 향함)에서 잰 것이다. 이 조건은
FaceLandmarker 의 **최악 케이스**다 — 추적할 얼굴이 없으면 검출기(BlazeFace)가 매 프레임
**전체 프레임**을 훑고, 이 단계가 소스 해상도에 정비례한다. 얼굴이 있으면 이전 랜드마크로
ROI 만 크롭하는 추적 모드로 들어가 비용 성격이 달라진다.

즉 **얼굴을 넣고 잰 값이 실사용 수치**이며, 그 측정이 없으면 "30fps 미달"이라고 확정할 수 없다.

종전 빌드 동일 조건 기준선: 얼굴無 `Detect 31 / infer≈21ms`, 얼굴有 `Detect 30 / infer≈35ms`.

`CLAUDE.md` 성능 기준: 프레임 레이트 30fps+, 검출 지연 33ms 이하.

> ⚠️ **A1 이 최대 위험**이다. 코드 주석에 선례가 기록돼 있다 — 프리뷰를 4K 급으로 올렸을 때
> (프리뷰 + 분석) 조합이 하드웨어 지원 범위를 벗어나 바인딩이 실패했고, **분석을 640×360 으로
> 낮춰도 동일**했다. 현재 프리뷰는 1920×1080 + `PREFER_HIGHER_RESOLUTION_OVER_CAPTURE_RATE`
> 라 여유가 있는지 실측으로만 알 수 있다.

## 5-b. 실측 결과 (2026-07-31, SM-X920 가로, 얼굴 프레임 내)

| | 512×288 (현행) | 1280×720 |
|---|---|---|
| Detect FPS | **30** | **27** (표본 26/27/28/27/25) |
| infer | ≈35ms | ≈34ms (**거의 불변**) |
| Render FPS | 60 | 60~61 |
| 바인딩 | OK | OK (조합 제약 안 걸림) |

**비용의 출처가 추론이 아니다.** 얼굴이 있으면 MediaPipe 는 추적 모드(ROI 크롭)라
추론 시간이 거의 그대로였다(35→34ms). 떨어진 몫은 **CameraX YUV→RGBA 변환·전송**
(6.25배 픽셀) 쪽이다. 얼굴이 **없을 때만** infer 가 21→32ms 로 튀는데, 이는 검출기가
전체 프레임을 훑는 최악 케이스라 실사용 경로가 아니다.

### 왜 갱신률 하락이 정밀도 이득을 상쇄하는가 (사용자 지적)

렌더는 60fps 인데 랜드마크 갱신이 30fps→27fps(33ms→37ms)로 벌어지면:

1. **렌더 2~3프레임이 같은 랜드마크를 재사용**한다. 그 사이는 보간/스무딩이 메우므로,
   프레임당 정밀도를 6.25배 올려도 **'눈에 붙어 있는' 체감은 갱신률이 지배**한다.
2. **`OneEuroFilter` 지연은 샘플 수 기준**이다. 초당 샘플이 줄면 같은 필터 설정이라도
   **벽시계 지연이 ~11% 길어진다.** 정밀도를 사고 반응성을 두 번 판 셈이다.

체감 형태는 `fsync` 설정에 달렸다 (`CameraGLRenderer.selectFrameSyncSlot`):

| | 동작 | 증상 |
|---|---|---|
| `fsync:on` (현재) | 랜드마크가 계산된 **그 프레임**의 링 슬롯에 렌즈 합성 | 렌즈는 눈에 정확히 붙되 **화면 전체가 지연·끊김** |
| `fsync:off` | 항상 **최신** 프레임 + 이전 랜드마크 | 영상은 즉각적이나 **렌즈만 눈을 뒤늦게 따라감** |

어느 쪽이든 Detect FPS 하락은 악화 방향이다.

## 6. 결론 — 판정 이월 (기각 아님)

**기본값 960×540 유지**(태블릿 512×288). 1280×720 은 **정밀도↑ / 갱신률↓** 맞바꿈이고,
두 값 사이에 중간이 없어 "조금만 올리기"가 불가능하다.

**판정을 렌즈 렌더링 트랙으로 이월한다.** 이유: 랜드마크 정밀도의 **최종 소비자가 렌즈 정합**이라,
정밀도 이득은 렌즈를 켠 상태에서 홍채 정합과 **함께** 봐야 판단이 선다. 정밀도만 따로 보면
"마커가 조금 더 붙는 것 같다" 수준의 미묘한 판정이 되어 [[feedback-qualitative-device-judgment]]
가 경고하는 함정에 빠진다.

> 같은 트랙에 이월된 항목: **SHARP G4 홍채 정합 육안 재확인** (진단 제거 후 캡처로 못 닫음 —
> 렌즈는 정상 활성이었고 `nativeRenderLensTexture 1080x1920` 불변식은 확인됨).

**그때 함께 판단할 것**
1. 1280×720 의 정밀도 이득이 렌즈 정합에서 눈에 보이는가
2. 보인다면 Detect 27fps 를 수용할 것인가 (프로젝트 30fps 기준의 명시적 예외가 된다)
3. 아니면 **단일 스트림 경로**로 가서 맞바꿈 자체를 없앨 것인가 ← 유력

## 7. 대안 (상향을 실제로 하기로 할 경우)

1. **폴백 규칙을 `CLOSEST_HIGHER_THEN_LOWER` 로** — 요청은 960×540 유지하되 위쪽으로 붙인다.
   결과는 같은 1280×720 이라 비용 문제는 해결되지 않는다.
2. **분석만 4:3 으로** — 태블릿 4:3 목록에 960×720 이 있다면 면적 절충이 가능하나,
   **프리뷰와 종횡비가 달라져 랜드마크 정규화 좌표 대응이 깨진다.** 좌표 변환 추가가 필요해
   비용이 크고 위험하다. 권장하지 않는다.
3. **단일 스트림 트랙으로 흡수** — 근본 해법. `ensureAnalysisTarget`(`CameraGLRenderer`)이
   프리뷰 텍스처에서 GPU 로 직접 다운샘플을 만들면 카메라 조합 제약 자체가 사라지고 크기를
   자유롭게 고를 수 있다. 현재 미배선이며 **배선 시 치수와 회전을 반드시 함께** 바꿔야 한다
   (SHARP §7-4-4 — 반쪽만 바꾸면 렌즈가 3.16:1 타원).
